# 技術策略：台股即時監控服務

> 記錄這個服務的技術路線、關鍵取捨的理由、以及未來架構走向。
> （工作流程方法論請看 `開發策略與流程.md`；單次變更細節看各「計劃／回顧」文件。）

---

## 1. 願景與成功標準

**一句話**：在交易時段穩定、即時地把全上市股票的漲跌反映到 Notion，並對 VIP/VVIP 觸價發信。

**成功標準**：
- **不漏股**：每輪所有監控標的都被更新到。
- **夠即時**：分鐘級更新（盤中價格連續變動）。
- **可靠可回滾**：抓價來源出問題能快速切換退路。
- **成本可控**：不被任一外部 API 的流量限制卡死。

---

## 2. 核心技術路線：從「逐支拉取」轉向「整批快照」

| | 舊：Fugle 逐支 quote | 新：富邦 snapshot |
|---|---|---|
| 抓取模式 | 一支股票一次 API（pull per stock） | 一次抓回整個市場別（pull whole market） |
| 流量 | 60/min，需多金鑰＋三層重試 | 300/min，一輪幾次呼叫即覆蓋全市場 |
| 漏股風險 | 高（限流／重試仍漏） | 無（整批回傳） |
| 並行複雜度 | 多 `API_Worker`＋節流＋備援 | 單執行緒、無節流 |
| 頻率上限 | 受限流，5 分鐘 | 1 分鐘（甚至更快，但無必要） |

**策略決定**：抓價端的根本瓶頸從「API 呼叫次數」消失，因此**抓價層大幅簡化**，複雜度移除而非搬移。

---

## 3. 關鍵取捨與理由

### 3.1 不換系統，用開關切換（`PRICE_SOURCE`）
- 舊 Fugle 路完整保留，`fubon`/`fugle` 一鍵切換。
- **理由**：降低遷移風險、保留退路；下游（Notion/email/VIP）共用，避免兩份會分歧的程式。

### 3.2 頻率定在 1 分鐘，而非每秒
- 台股盤中是**逐筆連續撮合**，每秒價格確實會變，但：
- **真正瓶頸是 Notion 寫入**（流量限制以 API key 為單位），不是富邦。
- 本服務是**監控／觸價警示**，非當沖看盤，秒級無實際價值。
- **策略決定**：抓價可以很快，但更新頻率由「Notion 寫入吞吐 × 業務需求」決定，定在 1 分鐘。

### 3.3 只寫「有變動的」——分鐘級去重
- 與上一輪同價的股票直接跳過，不寫 Notion。
- **理由**：把有限的 Notion 寫入額度花在真正變動的股票上，是 1 分鐘頻率能成立的關鍵。

### 3.4 顏色/漲跌幅直接取自快照
- `base_price = lastPrice - change`、`changePercent` 直接用。
- **理由**：資料自洽、即時，並逐步擺脫對 `df_base_data.json`（前日收盤）的依賴。

### 3.5 多市場別合併（重要教訓）
- 「上市」在富邦快照 ≠ 單一 `TSE`：**創新板(TIB)、上櫃(OTC)、興櫃(ESB) 各自獨立市場別**。
- 解法：查多個市場別並合併成單一查表（預設 `TSE,OTC,ESB,TIB`，可設定）。
- **教訓**：市場別的領域知識會直接影響「不漏股」這個成功標準，假設要用真實資料驗證。

### 3.6 新聞與股價解耦
- 股價 1 分鐘、新聞最多 5 分鐘；新聞爬蟲（Selenium，目前有問題）不拖累股價更新節奏。

---

## 4. 目前的瓶頸與擴展策略

- **瓶頸已從抓價端移到 Notion 寫入端**（每 API key 有流量限制）。
- **水平擴展**：`NOTION_API_KEY_LIST` 多把金鑰、多 `Notion_update_worker` 並行；不夠就加金鑰。
- **第一輪偏慢**：開盤首輪相對昨收幾乎全變動，寫入量大、可能 > 60 秒；之後靠去重恢復正常。
- **優化方向**：只寫有變動（已做）；未來可評估批次更新／減少每筆 payload。

---

## 5. 未來架構走向（Roadmap）

依優先序，待討論：

1. **完成富邦遷移驗收**：補跑 V4 端到端、上線前關閉 `SIMULATE_PRICE_CHANGE`。
2. **重啟 VIP/VVIP 與 email**：目前 `main.py` 的 VIP 抓取/寄信為部分關閉狀態，遷移穩定後恢復。
3. **退役 `df_base_data.json` 對漲跌幅的角色**：顏色/漲跌幅已改用快照；評估盤後更新流程是否還需要。
4. **Pull → Push 的可能性**：富邦提供 WebSocket 即時行情推送。若要更即時或更省呼叫，可評估從「每分鐘拉快照」改為「訂閱推送、事件驅動更新」。但需權衡複雜度與 Notion 寫入仍是瓶頸這件事。
5. **修復新聞爬蟲**：Selenium 流程現有問題，獨立修。
6. **正式環境部署**：GCP + Secret Manager（`utils/gcp_config.py` 已有雛形）取代本機 `.env`。

---

## 6. 風險與待解問題

- **富邦連線穩定性／登入 session 失效**：目前登入一次重用，需確認長時間運行下 session 不會過期；若會，要加重連機制。
- **Notion 寫入吞吐天花板**：監控標的成長時，1 分鐘是否撐得住，需用真實量壓測。
- **市場別涵蓋變動**：未來若監控清單加入新板別，`FUBON_SNAPSHOT_MARKETS` 要同步。
- **快照 vs 真實成交時間差**：`lastUpdated` 與我們寫入 Notion 的時間落差是否在可接受範圍。

---

## 7. 一句話總結策略

> **抓價端用「整批快照」徹底解決漏股與限流；把省下來的複雜度與額度，集中投資在「只更新有變動的、撐住分鐘級頻率」上；舊路保留為退路，未來視需要再從拉取走向推送。**
