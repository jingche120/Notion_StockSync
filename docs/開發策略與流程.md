# 開發策略與流程（Playbook）

> 這份文件記錄「我們一路以來怎麼推進工作」的方法論，當作之後可重複套用的標準流程。
> 與技術細節無關（技術記錄請看各次的「計劃」與「回顧」文件），這裡只談**流程**。

---

## 0. 核心精神

1. **先對齊，再動手**：需求沒確認一致前不寫碼、不擬細部計劃。
2. **文件先行**：實作前先有「施工＋驗收」文件，白紙黑字、可被第三方對照。
3. **獨立驗證**：用乾淨 context（subagent／另開 session）當第三方驗收，避免「自己驗自己」的確認偏誤（confirmation bias）。這套「實作→驗證→修正」的循環就是 **evaluator-optimizer loop**。
4. **保留退路**：改架構時舊路完整保留，用開關切換，可一鍵回滾。
5. **不可逆的事先確認**：刪檔、寫正式資料庫等，先列清單／先說明，等同意再做。

---

## 1. 標準流程（七步）

```
① 需求討論與對齊  →  ② 擬定計劃＋驗收文件  →  ③ 使用者審閱同意
       →  ④ 實作（todo 追蹤）  →  ⑤ 自驗（靜態＋單元）
       →  ⑥ 獨立驗證（subagent／另開 session）  →  ⑦ 修正迭代 → 回顧文件
```

### ① 需求討論與對齊
- 使用者說需求 → 我**用自己的話複述理解**，並列出影響方案的**關鍵問題**請使用者回答。
- 對齊「共識表」後才往下。**不在這步寫計劃細節。**

### ② 擬定計劃＋驗收文件（`docs/xxx計劃.md`）
- 內容：背景與目標、共識、**施工項目（Task，指明改哪個檔）**、**驗收方式（V1…Vn，每項標「怎麼驗」）**、風險、回滾。
- 驗收項目要能被獨立第三方照著跑。

### ③ 使用者審閱同意
- 計劃交付後，**等使用者點頭**再實作。期間的選擇用提問釐清。

### ④ 實作
- 嚴格照計劃的 Task 清單，**不擴大範圍**（明確標示「不動哪些檔」）。
- 用 todo 追蹤進度。

### ⑤ 自驗（我先擋一輪）
- 靜態：import、編譯、`git diff` 確認沒動到禁改檔。
- 單元：核心邏輯用 mock 快速驗（不需外部連線那部分）。

### ⑥ 獨立驗證（第三方把關）
- 交給乾淨 context 的驗證者，指令三要素：
  1. **只驗證、不要改任何程式碼**
  2. **逐項對照驗收清單**回報 通過／不通過／無法驗證
  3. **附證據**（git diff、實際 log、指令輸出），禁止「看起來沒問題」
- 兩種載體：**subagent**（我派，方便、結果回同一對話）／**另開 session**（使用者開，最中立）。

### ⑦ 修正迭代 → 回顧
- 驗證者回報問題 → 修 → 再驗，直到驗收清單全綠。
- 收尾寫「回顧文件」（`docs/工作回顧_xxx.md`）：做了什麼、發現的 bug、教訓。

## 2. 名詞對照（我們用到的做法叫什麼）

| 我們的做法 | 業界名稱 |
|---|---|
| 用另一個 AI／session 驗證 | **LLM-as-a-judge** |
| 一個產出、一個驗證並回饋迭代 | **Evaluator-Optimizer loop**（也叫 Generator-Verifier / Actor-Critic） |
| 同 session 內派出的獨立代理 | **subagent（子代理）** |
| 自己驗自己會偏袒 | **confirmation bias（確認偏誤）** |

> 注意：Claude Code 的 `/loop` 是「定時重跑指令」的排程工具，**與這裡的驗證迴圈無關**。

## 3. 落實到本專案的慣例

- **抓價來源切換**：`PRICE_SOURCE=fubon|fugle`，改架構不刪舊路（退路）。
- **測試行為用旗標**：如 `SIMULATE_PRICE_CHANGE`，預設關閉、絕不污染正式環境，上線前必關。
- **機密走 `.env`**：帳密、憑證路徑不寫死在程式碼。
- **刪除前先列清單**（專案規則）：移除股票、封存 Notion 頁面等，先確認再動。
- **文件三件組**：每個較大的變更 →「計劃＋驗收」「回顧」（必要時）「本流程文件」更新。
